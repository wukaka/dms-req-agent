# dms-req-agent

用一群 agent 替人去系统里取证，产出数据采集需求文档。**机器能自己证的绝不问人，只有业务判断才找人，而且一次问完。**

---

## 1. 这活儿本来是怎么干的

把 DMS 的数据接进数仓之前，得先有一份采集需求文档。要采哪 6 张业务表是定好的，
每张表有哪些标准字段、粒度要求是什么，也是定好的。剩下的问题只有一个：**这些字段在真实系统里到底有没有，从哪儿取。**

于是有人坐到电脑前。登录后台，顺着菜单一路点进去——订单管理、我的订单、列表页、详情页；
打开开发者工具，翻出刚才那次点击触发的 XHR，对着响应体一个字段一个字段地核：
订单号在这个接口里叫 `orderNo`；状态给的是 `90`，得去站点字典里翻出它是“已完成”；
金额列没有单位字段，那这一项就只能记“无法采集”，不能自己推断成“元”。
核完一张表，把结论抄进文档，再换下一张。

6 张表，几十个字段，一个人几天。累还不是最要命的，要命的是这活儿只有人能判断，
而它又最怕判错：

- **现场只有一个。** 登录态是单点的，刷新一下可能就得重新登录，刚抓住的证据就断了。
- **判断是业务性的。** 契约要“月度账单”，站点只给半月期号——按实际粒度采，还是判不适用？
  机器只能把事实摆出来，采不采得人拍板。
- **错了全在后头。** 这份字段表是下游写采集器、解析器、校验器的唯一依据。一个字段的来源
  写错，下游全错，而且要很晚才会被发现。

所以这一步的人力大约是：表的数量 × 每张表的字段数 × 每个字段的取证成本，再加复核成本。
而这里面有一条很干净的分界线：**取证可以全部交给机器，判断不能。**

这就是本项目的全部立足点——把人从逐页排查里换出来，只在非人不可的地方出现，而且一次问完。

## 2. 骨架

人干这件事的顺序是先摸清整个系统、再一张表一张表核。机器接过来之后，顺序没变，
只是拆成了三棒，而且中间那一棒可以同时开六张表的工：

```
                    ┌──────────────────────────────────────────┐
   第一棒            │ Discovery                                │
                    │ 抓全量菜单树 → 6 张表逐个"轻点确认"       │
                    │ 产出：五态初判 + 入口 + 锚点 + 同源提示   │
                    └────────────────────┬─────────────────────┘
                                         ↓
                    ┌──────────────────────────────────────────┐
   第二棒（扇出）    │ 业务 agent × N（每张表一个，名字=表名）   │
                    │ 第一段：判定（存不存在、粒度对不对）      │
                    │ 第二段：字段映射（仅在第一段放行时）      │
                    └────────────────────┬─────────────────────┘
                                         ↓
                    ┌──────────────────────────────────────────┐
   第三棒            │ Judge                                    │
                    │ 运行中：跨表提问（先查表，后挂模型）      │
                    │ 收尾：一致性自检 → 合稿                  │
                    └────────────────────┬─────────────────────┘
                                         ↓
                          两份文档：采集需求 + 技术笔记

   贯穿全程：每一步结论实时落盘；人在检查点插入；重跑从落盘处续做
```

6 张表（契约顺序，也是文档章节顺序）：

`dms_basic_info` · `dms_order_details_info` · `dms_bill_monthly_info` ·
`dms_bill_details_info` · `dms_contract_sign_info` · `dms_certified_info`

平台目录里的落盘产物：

| 文件 | 是什么 |
|---|---|
| `manifest.json` | **唯一的进度真相**：每张表的存在性判定、入口、待人工问题、检查点开关、人已豁免的检查项 |
| `evidence_index.json` | 字段级证据索引：路径 / 类型 / 样例（封顶 2 条）/ 对应哪个标准字段 |
| `menu_map.md` | 全量菜单树。"这张表不存在"的证据链 |
| `tables/<表名>.md` | 每张表的分片文档草稿，人审的就是它 |
| `files/<表名>_*` | 原始响应存档（HTML/JSON/Excel），文件名前缀即所有权 |
| `images/` | 阶段三的红框标注截图 |
| `questions.md` | 本轮需要人看的全部问题 |
| `logs/agent_events.jsonl` | 带 agent 归属的事件流（见第 6 节） |
| `blackboard.md` | 站点经验，跨轮次累积 |

## 3. 人什么时候出现

流程故意切成几轮，每轮之间都是一个可以停很久的检查点：

```
第 1 轮  Discovery 跑完 → 落盘 → 有几张表判 pending_human → 写 questions.md → 退出
         人对照 menu_map.md 拍板存在性，改 manifest.json
第 2 轮  业务 agent 扇出 → 逐表落盘 → 部分表留下 deferred_questions → 写 questions.md → 退出
         人解决掉那些问题，改 manifest.json
第 3 轮  五条一致性自检 → 干净 → 写 questions.md 请人审字段映射 → 退出
         人审完在 manifest.json 里把 fields_confirmed 设为 true
第 4 轮  截图 agent 跑 → 合稿 → 两份文档落盘 → phase = done
```

这个切法的意义是省人力，而且省的不是分钟数：

- **人不必待命。** 进程允许退出，人也允许过几天再来。
- **问题是批量的。** 一轮答完，人的上下文切换从 N 次降到 1 次。
- **回答方式是改文件。** 拍板存在性就改 `existence`，审完就改 `fields_confirmed`，
  判某条一致性检查可以接受就把它的全文贴进 `acknowledged`——没有"回答"这个 API，也没有审批流。

## 4. 六条主张

下面这些主张，基本都被同一件事逼出来：**人不在现场，而且只能回来一次。**

### 4.1 进度真相在磁盘，不在内存

框架的默认气质是"一个 session 就是一个世界"，退出即失忆。这里反过来：
`manifest.json` 是唯一进度真相，任何内存对象都不跨进程存活。

**人能改**是主要理由（见第 3 节）。另外两条是保险：所有落盘走临时文件 + `os.replace`，
不会读到半个 JSON；不认识的字段一律保留，因为阶段 2–5 也会往同一个 manifest 里写东西。

有个细节能说明这个取舍：Discovery 的输出模型在代码里**禁止** `existence: absent`
（它只能提名，不能终判），但续跑时读的是**普通 dict** 而不是 pydantic 对象——
人要在两次运行之间手改出 `absent` 这个值来。**严格的模型管生成，宽松的 dict 管续跑。**

### 4.2 判定优先：允许"一张表都不交"地成功

每张表的 agent 分两段跑，中间有一道门：

```
第一段：判定   载体唯一吗？粒度对吗？  → exists / partial / absent / granularity_mismatch / pending_human
                  ↓ 只有 exists / partial 放行
第二段：字段映射
```

**门禁写在代码里，不是写在提示词里。** 第二段的入口只有 `run_table_agent()` 一个，
第一段判定非产出态时它直接返回。所以"这张表不该做字段映射"不依赖模型读懂规则，也不依赖它听话。

原则是：**一个 agent 必须能"一张表都没交"而算成功。** `absent`（不存在）和
`granularity_mismatch`（粒度不符）都是合法结论，不是失败——真实例子就是契约要月度账单、
站点只给半月期号（`fileNameMonth` 形如 `260801`）。把它并进 `absent` 或勉强算 `exists`，
等于把业务决策偷偷替人做了。

### 4.3 判定纪律：能提名的不终判，能下钻的不早退

- **Discovery 不下 `absent` 终判**，只提名，由人对着菜单树确认。零命中太容易来自
  "我没找到"，而不是"它不存在"。
- **`partial` 要保守**：列表页看着缺字段不算缺字段，标上"可能还有详情页"继续下钻。
- **业务 agent 的判定覆盖 Discovery 的判定**，分歧记进 `dissent_from_discovery`。
  Discovery 只轻点确认了一下，业务 agent 才是实地核验的人。

### 4.4 确定性的归代码，语义的才挂模型

Judge 的两个时相都守这条。**运行中答疑**的解析顺序是：查 `evidence_index.json`（纯查表）
→ 查 `files/` 原始响应（需要时挂模型）→ 都答不上就攒成 blocker，收尾一次性问人。

**收尾的一致性自检**有固定五条，任一条命中就拦住合稿：

| # | 检查 | 实现 |
|---|---|---|
| ① | 表级否定与"存在"判定冲突 | 正则粗筛 + 模型判否定作用域 |
| ② | 载体唯一性（判 `exists` 就得指得出接口，且接口不能整体属于别的表） | 纯代码 |
| ③ | 粒度核对（对声明了粒度要求的表） | 正则 + 模型 |
| ④ | 锚点一致性（各表的 `distributor_code` 必须来自 Discovery 定的那口径） | 纯代码 |
| ⑤ | 一对一原则（同表内一个标准字段只能有一个来源，反之亦然） | 纯代码 |

**为什么必须机器可查**：文档里的散文和结构化判定不一致时，人几乎看不出来（正文写"不存在"、
状态写"完成"，两边都像是正常的），而下游会照单全收。所以一致性不能靠模型自觉，得有代码关卡。

① 最能说明"两级判定"的必要性。"无重量相关字段"是**字段级**否定，完全合法——那正是
"无法采集"该有的说法；"该后台无月度账单"是**表级**否定，和 `exists` 并存就是自相矛盾。
纯正则会误杀，纯模型会漏，所以先正则粗筛、再把命中项交给模型判作用域。

一条检查如果确实该放过，人把它的全文加进 `manifest.json` 的 `acknowledged` 就豁免了。
按全文匹配是故意的：底层证据一变，文字就变，这条 finding 会重新冒出来，而不是被永久压住。

粒度要求也不是硬编码字典，而是写在字段提示词（`prompts/fields/<表名>.md`）的 frontmatter 里——
**契约和字段定义同一份文件，只有一个真相源。**

### 4.5 人在回路里，做成通信协议而不是交互 UI

框架默认的人机交互是终端弹确认框。这里的假设相反：人不在旁边。所以接口拆成两条路：

- **进程内**：agent 需要裁决时挂起自己等一个 future；对面可以枚举"谁在等什么"、逐条回答、
  给某个 agent 发指令、中止某个 agent。
- **进程外**：待办写进 `questions.md`，进程**允许退出**；人改 `manifest.json`，重跑续做。

两条路共用一套命令面（第 6 节），区别只是"谁在对面"。

### 4.6 多 agent 的典型失效模式，用结构删掉

不靠提示词劝 agent"别聊了"，而是让这些失效模式不成立：

| 失效模式 | 结构上怎么被删掉 |
|---|---|
| agent 之间互相咨询停不下来 | 追问链深度上限 1：Judge 的回答不再生成新问题 |
| 把预算烧在提问上 | 每个 agent 提问预算 3 次，用完基于现有证据下判断 |
| A 持着浏览器等 B 回话，B 在排队等浏览器 → 互等死锁 | 提问工具不是浏览器工具，不经过取号；**结构上不可能持号提问** |
| 并行后没人"先跑"，各表口径漂移 | Discovery 先定锚点，所有 agent 无条件遵守 |
| 两张表同源却重复取证 | Discovery 记同源提示（真实例子：月账单与账单明细是同一个接口，明细在 `detailList[]`） |
| 一张表读到另一张表的产物 | 档名即所有权（`tables/<表名>.md`、`files/<表名>_*`），越界直接拒写，不需要额外账本 |
| 一张表失败连累整批 | 逐表落盘：后跑的表失败，不会让先跑完的表丢工作 |
| teardown 抛异常把真实原因盖掉 | 收尾吞掉自己的异常，但把吞掉的事实记进事件流 |

## 5. 和 AgentScope 2 官方设计的逐条对照

**"不一样"不是不用 AgentScope，而是不照它的架构范式搭。** 框架能表达的一律用它的扩展点，
框架表达不了的才自建；自建的两样（跨进程的进度真相、可中断可续跑的双向通信）
恰好是框架没有建模的两样。

下面每一条，框架里都有对应的标准路径。没走，是因为它们的默认前提在这儿都不成立：
人就在旁边守着、工具调用怎么用都安全、进程一直活着、会话断了还能自己回来。

| 官方默认 | 为什么不走 | 我们走哪条 |
|---|---|---|
| 每个角色一个 Agent 子类 | 2.0.8 里没有 `ReActAgent` 子类，只有基类 `Agent`；角色差异只在提示词、工具面和调用协议上 | 全部基类 `Agent` + `ReActConfig`，角色差异用**数据**表达，不用类 |
| `agent.reply()` | 它等于 `reply_stream(yield_final_msg=True)` 再把事件全丢掉——结构化输出拿到了，过程全丢 | 自己消费 `reply_stream`：结构化输出在最终消息里，**顺带**拿到全过程事件流 |
| `is_external_tool=True` 暂停等人工 | 这条路径会**结束** reply 流，要靠回放 `ExternalExecutionResultEvent` 开一次**新的** `reply_stream` 才续得上，而"一次调用出结构化结果"的契约装不下跨调用续跑 | 用普通异步工具 await 一个 future：一样挂起 agent，流的生命周期不被打断，等待逻辑留在自己代码里 |
| `UserInterruptEvent` 注入人工指令 | 它只是清掉暂停态，**推不进正在运行的 agent** | 在 `on_reasoning` 钩子里把消息以 `HintBlock` 追加进 agent 状态（与框架自己做运行时状态注入同一机制） |
| 默认权限模型（非只读工具先 ASK） | 无人应答时 `reply()` 会**静默提前结束**（`finished_reason=None`），三层之外表现为莫名其妙的"没有 structured_output"崩溃 | 用 `BYPASS`；安全前提是工具面在上游已被白名单削过一遍 |
| 会话 / 内存即状态 | 进程一退全丢，人也无法介入 | `manifest.json` 是唯一进度真相，人改文件就是介入 |
| 把 MCP 工具直接交给 agent | 模型看到 schema 就可能调用，而这里是"已登录会话绝不导航/刷新" | MCP 客户端层先 `disable_tools` 掉 `navigate_page` / `new_page`——**模型根本看不到这两个工具的 schema** |
| 官方 formatter / model 直接连 provider | 遇到两个确定性的 provider 400（见下） | 两个薄子类：一个重排被图像提升打乱的消息顺序，一个把不支持的强制单工具选择降级为 `auto` |
| `MiddlewareBase` 扩展点 | — | **照用。** 浏览器串行是 `on_acting` 的一个实现，人工指令注入是 `on_reasoning` 的一个实现 |

两个 provider 兼容问题看起来像竞态，其实都是确定性的：

1. 官方 formatter 会把工具结果里的图像提升成一条额外的 `user` 消息，紧跟工具消息之后。
   截图恰好是那一轮最后一个工具调用时没事；模型一次并发调两个工具时，这条消息就卡在两条
   `tool` 回复中间，触发"每个 tool_call 都必须有对应回复"的硬规则。
2. 到达 `max_iters` 而结构化输出还没交出来时，框架强制 `tool_choice=<工具名>` 逼 agent 提交，
   DeepSeek 的思考模式直接拒绝这个参数。

### 5.1 浏览器单点 = 框架的 tool 调用管理

这里没有自研调度器。浏览器串行就是一个 `MiddlewareBase.on_acting`：一次恰好包住一个
`toolkit.call_tool`，这是这套机制能挂的**最窄**粒度。

```
on_acting(一次 tool 调用)
    ├─ 是浏览器工具？ → 取号（容量 1 的信号量）→ 执行 → 还号
    └─ 不是          → 直接放行
```

它只做一件事：**把外部世界的一条不变量翻译成中间件**——浏览器是全局单点，
CDP 的 current-page 是全局状态。所以容量 1、无 tab 注册表、无租约超时。

两个容易踩的点：

- **"提问前必须释放号牌"是结构保证的。** `ask_human` / `ask_judge` 不是浏览器工具，
  压根不进 `on_acting` 的保护分支，所以不存在"显式释放"这回事，持号提问不可能发生。
- **命名空间要显式转换。** 中间件比较的是 `tool_call.name`，而框架已把 MCP 工具重命名成
  `mcp__{client}__{tool}`；`enable_tools` / `disable_tools` 过滤的才是服务端裸名。
  不加这一次转换，**串行保证会静默失效**：中间件永远匹配不上，什么都不拦，也不报错。

一个诚实的补充：`disable_tools` 只过滤 `list_tools()` 的结果，按名字
`get_tool("navigate_page")` 仍拿得到。所以"绝不导航"这条保证依赖一条代码纪律——
**任何地方都不准按名字取工具，只能把过滤后的列表注册进 Toolkit。**

## 6. 联邦化的 agent 群，怎么和外层 CLI 双向通信

场景：一个像 Claude Code 那样的 CLI agent（下面叫"驱动者"）把本框架跑起来，
然后要跟内部这一群联邦化的表 agent 双向通信——看它们在干什么、在等什么、
给某一个发话、必要时掐掉某一个。

### 6.1 第 0 原则：表名是唯一地址

驱动者不跟"agent 群"对话，它跟**具名的表**对话。框架内部三张按名字索引的表负责解析：

| 组件 | 按名字管什么 |
|---|---|
| `TableTaskRegistry` | 正在跑的任务（按名字中止、列出还在跑的） |
| `AgentMailbox` | 待投递的指令（按名字排队） |
| `HumanChannel` | 正在等答复的问题（按名字 + 问题 id） |

**agent 的身份就是它的表名。** 于是不用分配 id、不用维护"哪个 agent 是哪个"的映射，
人的直觉和机器的索引是同一个东西。截图阶段另起一个 agent，名字是 `<表名>-screenshot`，
所以同一张表的两段工作也分得开。

### 6.2 上行：可归属的事件流

并发扇出后，MCP 自己往 stdout 写的行是没法归属的——没人知道是哪张表写的。
所以这里自己消费 `reply_stream`，把每个事件交给 `EventSink`，再 `tee()` 给两个下游：

```
agent 的事件 ──┬──> JsonlEventLog   （append-only，每条带 agent 字段，保留并发的真实交错）
              └──> ConsoleSink     （终端渲染，带 agent 标题）
```

**对机器调用者，通道是那份 jsonl，不是终端渲染。** 一个文件保留真实交错、一个 `agent`
字段可事后过滤，比"每个 agent 一个日志文件"更有用——后者看不出谁先谁后，
而"谁先谁后"恰恰是排查并行问题的全部线索。

`tee()` 里每个 sink 各自 try/except：终端渲染炸了不该让一张表陪葬，也不该让持久日志丢掉那一份。

### 6.3 下行：三种语义，三条通道

| 意思 | 通道 | 语义 |
|---|---|---|
| **裁决**（它卡住了，等一个判断） | `HumanChannel.ask()` → future | 挂起在工具里，流不中断；`pending()` 看在等什么，`answer(question_id, text)` 作答 |
| **指令**（改它的计划，但不打断） | `AgentMailbox.send(表名, 内容)` | 该 agent 下一次推理前读到，且被标注为"优先于你当前计划" |
| **中止** | `TableTaskRegistry.cancel(表名)` | 按名字取消一个任务，其它表不受影响 |

三点：

- **指令是"下一步才生效"，不是打断。** 注入在推理前，不插进正在进行的推理——
  这样每一步都是完整的决策单元，不会产生半成品状态。
- **中止之后没有"恢复"，只有"重跑"。** 被中止的表本轮无结论，重跑以 `manifest.json` 为准。
  这消灭了"部分完成、状态可疑"这一整类麻烦。能靠重跑解决的，不要做恢复。
- **取消是一种决定，不是故障。** 人工中止单独一类，措辞不写成"登录态/MCP 断连"，
  否则运维会去追一个不存在的 bug。

这三条通道落到操作台上，就是六个命令：

```
q                      列出等待人工回答的问题
a <表名> <答案>        回答某张表的问题
ps                     列出仍在运行的表
kill <表名> [原因]     中止某张表（其它表不受影响）
msg <表名> <内容>      给某张表发一条指令，它下一步推理前会读到
help                   显示本帮助
```

命令行入口只是一层薄包装：解析参数、跑一轮、把本轮变化打印出来。进度真相在磁盘，不在它的输出里。

### 6.4 命令面不绑 TTY：这是能对外通信的关键

```python
OperatorConsole.dispatch(line) -> str    # 同步、纯函数、不碰 stdin/stdout
OperatorConsole.run()                    # 才去绑终端
```

`dispatch()` 同步、进一行字符串、出一行"要打印的话"。**所以整个命令面可以脱离终端被测试，
也可以被任何不是终端的调用者驱动。**

```
        人（TTY 适配器）        外层 CLI（工具调用适配器）
                \                    /
              dispatch(line) -> str        <-- 同一个命令面
                 /                  \
     HumanChannel（裁决）  AgentMailbox（指令）  TableTaskRegistry（中止）
```

**"人"和"外层 CLI"是同一命令面的两个适配器**，一个从 stdin 读，一个从工具调用读，
框架不知道对面是谁。

驱动者今天接进来用的是三样已存在的东西：

1. `dispatch()` 那个命令面——同步、无终端依赖，本来就是按"可被机器调用"设计的
2. `logs/agent_events.jsonl`——上行事件流
3. `manifest.json` 的手改协议——`pending_human` / `deferred_questions` / `fields_confirmed` /
   `acknowledged` 四个开关，也就是进程外那条路

把这三样包成 MCP 工具（用工具调 `q` / `a` / `ps` / `kill` / `msg`，事件流推回去），
是同一命令面的**另一个适配器**，机制上不需要新东西。（这句是判断，不是已实现的代码。）

这个适配器层有个踩过的坑：读 stdin 用的是**守护线程**，不是 `asyncio.to_thread`——任务被
取消时，卡在 `readline()` 里的线程叫不醒，而 `asyncio.run()` 退出时会 join 默认执行器，
结果是所有表都跑完了，进程却挂在那里不退，屏幕上什么都不说。同理，操作台自己是被
`cancel()` 掉的，不是 `await` 完的：**没人在打字是常态，等 stdin 关闭就意味着流程永远结束不了。**

### 6.5 为什么值得这样设计

- **驱动者是可替换的。** 今天是人打字，明天是 CLI agent，后天可能是 web 控制台，
  共用同一个命令面，框架一行不用改。
- **通信语义是有限的三种，不是无限对话。** 而"无限对话"正是多 agent 系统失控的入口。
- **进程内 / 进程外两条路共用一套词汇。** 所以"人现在在不在"不影响设计，
  只影响这次跑要不要中途停下。
