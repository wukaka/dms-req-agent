# Judge agent

Judge 有两个时相：**运行中答疑**（业务 agent 之间的跨表提问由它机器化查表回答）与
**收尾合稿**（一致性自检 → 跨表复核 → blocker 汇总问人 → 合稿 → 写回 manifest）。

## 7. 证据索引与问答协议

### 7.1 evidence_index.json

每个业务 agent 边干边写自己那一段，目的是让跨 agent 提问能从磁盘答掉，不依赖被问的
agent 仍然活着（各 agent 时长不一，被问者很可能已退出）。

```json
{
  "dms_order_details_info": {
    "apis": [{"method": "GET", "url": "/mdlz-order/otc-order-main/detail", "file": "files/亿滋_订单明细_1_detail.json"}],
    "columns": ["订单编号", "下单日期"],
    "fields": [
      {"path": "main.orderNo", "type": "string", "samples": ["OTC2608010001", "OTC2608010007"], "mapped_to": "order_no"},
      {"path": "orderItems[].skuName", "type": "string", "samples": ["..."], "mapped_to": "product_name"}
    ]
  }
}
```

样例值封顶 2 条；完整响应存 `files/`，此处只存索引。`mapped_to` 使 Judge 能机器化地
做跨表一致性核查。

### 7.2 问答协议

```json
{
  "from": "dms_bill_details_info",
  "about": "order_no",
  "need": "order_no 的编码格式与 2 条样例",
  "scope": ["dms_order_details_info"]
}
```

解析顺序：查 `evidence_index` → 查 `files/` 归档原文 → 均答不上则转 blocker，攒到收尾
一次性问人。

**worked example（emdlz 的悬案）：** 账单明细 agent 手里是 `deliveryNo`，判不了它与
`order_no` 有无关系，现有结论是「编码体系不同，无关联证据」——含糊。走本协议：Judge
从索引取出 `main.orderNo` 的两条样例，agent 比对编码体系，要么确认可关联，要么**有证据地**
判不可采集。两种结局都优于现状。

### 7.3 约束

- **提问前必须先释放浏览器叫号**，否则 A 持号等 B 回话、B 又在排队等号，双方互等，死锁。
- **追问链深度上限 1**，禁止 agent 之间聊起来（多 agent 系统的典型失效模式是互相咨询
  取代干活）。
- **每个 agent 提问预算 3 次**，超出转 blocker。

## 8. 收尾：一致性自检、blocker 与合稿

### 8.1 两个时相

**运行中答疑**：主体是机器查询（查索引、查归档），仅在需要语义判断时调模型（例如
「这两个编码体系是否同一套」）。原则：能确定性映射的不挂模型。

**收尾合稿**：一致性自检 → 跨表复核 → blocker 汇总问人 → 合稿（产出两份文档）→ 由
orchestrator 落盘并置 `phase: "done"`。

### 8.2 一致性自检（五条）

这是拦住「散文与判定不一致」这类错误的关卡，必须机器可查，不能只靠 LLM 自觉。实现见
`checks/consistency.py`，`run_all()` 跑齐五条，任一条命中即拦住合稿。

**① 否定语义与判定冲突**（`check_negation_conflict`）。扫描 notes 与 `tables/*.md`
（Markdown 表格行除外，表格行天然是字段级）中的否定词——代码实际匹配的是
「无 / 没有 / 不存在 / 不提供 / 未发现 / 未见 / 缺少」，并特意排除「无法」
（"无法采集"是在判不可采集，不是在否定存在）。命中后判断**否定的作用域**：

- 「无重量相关字段」是**字段级**否定 → 合法，这正是字段表「无法采集」的用途
- 「该后台无月度账单」是**表级**否定 → 与 `exists` 并存即冲突，拦住合稿

**② 载体唯一性**（`check_carrier_uniqueness`）。`exists`/`partial` 的表必须指认得
出载体：入口的 `route`/`menu_path` 非空，且 `evidence_index` 中它有非空 `apis`；
其**接口集合**还不能整体落在别的表名下（代码比的是接口 URL 集合，不是字段），
除非这对表已在 `discovery.same_source_hints` 里声明同源（`dms_basic_info` 从
localStorage 加订单接口拼装会命中此条）。

**③ 粒度核对**（`check_granularity`）。对契约声明了粒度要求的表，检查粒度字段样例是
否符合（`fileNameMonth` 样例 `260801` / `260602` 为半月期号，机器可判定其非月度）。

粒度要求声明在 `prompts/fields/<表英文名>.md` 的 frontmatter 里，与该表字段定义同处
一份文件，`consistency.py` 在导入时从那里加载，不是硬编码字典。当前 6 张表中只有
`dms_bill_monthly_info` 有此要求（月度），其余为空即不检查。

**④ 锚点一致性**（`check_anchor_consistency`）。各表中 `mapped_to: "distributor_code"`
的 path 是否与 `discovery.anchors` 声明一致。

**⑤ 一对一原则**（`check_one_to_one`）。同表内两个标准字段映射到同一 path，或一个标
准字段映射到多个 path，均报告（现有字段规则 3 的机器化版本）。

②④⑤ 为纯代码检查；①③ 需 LLM 辅判（`consistency.py` 只做正则粗筛，作用域判断仍要
Judge 用模型确认）。

**任一条命中即拦住合稿**，转人工中断点②。

### 8.3 blocker 分类

- `blocking`：登录态失效、MCP 断连等——立即中断并报人工，不攒。
- `deferred`：字段语义拿不准、业务含义待确认等——攒到收尾一次性问完。

现有架构是一张表撞墙即打断人工一次；改为一轮答完。

### 8.4 合稿

两份文档的拆分规则沿用下方「模式 D：合稿」——那是已评审的资产，复用不重写。

**`absent` 与 `granularity_mismatch` 的表在主文档中必须有章节**，写明判定结论与证据，
不得省略。后续第 2–5 阶段需要能区分「这张表不做」与「这张表漏了」，缺了章节就无法区分。

## 模式 D：合稿

所有表都进入终态（非产出态当场终态；产出态要等字段映射落盘、人工确认、截图轮跑完），
且一致性自检与待人工问题都清零后，进入合稿。这一步是**纯离线**合稿（不需要连浏览器，
也不要连）；`phase` 没有中间值，合稿成功后由 orchestrator 直接置 `phase = "done"`。

**产出两份文档，从 `tables/*.md` 拆分内容，不是直接拼接**：

### ① `<平台名>采集需求.md`（主文档）

按固定 6 张表的章节顺序（与下方「文档结构模板」及 `manifest.json` 的 `tables[]` 一
致）：`dms_basic_info` → `dms_order_details_info` → `dms_bill_monthly_info` →
`dms_bill_details_info` → `dms_contract_sign_info` → `dms_certified_info`，每张表一
节，只保留：

- 一句话数据来源（页面路径 + 数据来源形态，不展开接口调用细节）。
- 字段清单表：沿用下方「字段采集表编写检查清单」的列（字段英文名 / 字段中文名 /
  字段编号 / 字段类型 / 示例 / 采集页面路径 / 采集规则 / 字段来源），一行一字段只写
  结论——「采集规则」列的取值就是"采集字段 / 无法采集 / 系统生成"，不另设「可采集」
  列；「不可采集」的表整张一句话说明，详细排查过程放技术笔记。
- 截图：`![<一句话>](images/<表名>_<板块>_<序号>-annotated.jpg)`（本文档与 `images/`
  同级，路径不带 `../`）。
- 「待人工确认」只列**仍未决**、需要人工现在就看一眼的问题。

补上系统概述（平台名、entry_url、测试账号、鉴权方式、数据返回方式、一句话登录方
式）、栏目地图引用。**目标篇幅**：单表一节控制在「字段表 + 一句话结论」的规模——论证
过程、排查清单、响应结构一律放技术笔记，超出就是没拆干净。

#### 文档结构模板

```markdown
# {系统名称} DMS 系统采集需求文档

## 系统信息
| 项目 | 内容 |
|------|------|
| 采集网站 | <URL> |
| 系统名称 | <系统名> |
| 系统架构 | <如 SAP Hybris> |
| 数据返回方式 | <SSR HTML / JSON API / SPA> |
| 鉴权方式 | <Header Token / Cookie Session / 自定义参数> |
| 鉴权字段 | <具体字段和获取方式> |

## 一、基础信息 (dms_basic_info)
## 二、经营信息-订单明细数据 (dms_order_details_info)
## 三、经营信息-账单分月数据 (dms_bill_monthly_info)
## 四、经营信息-账单明细数据 (dms_bill_details_info)      ← 无则强调不存在
## 五、基础信息-合同信息 (dms_contract_sign_info)      ← 无则强调不存在
## 六、基础信息-认证信息 (dms_certified_info)          ← 无则强调不存在
```

### ② `<平台名>技术笔记.md`（技术细节，供第 2–5 阶段参考）

每张表一节，装下 `tables/*.md` 里除字段清单外的全部技术内容：数据来源完整版、派生字
段规则、落库粒度/折叠规则的决策依据、不可采集字段/表的完整排查清单+核验日期、待补字
段的补采线索、全部待人工确认问题。这份文档**不是字段命名的信任来源**，第 2–5 阶段仍
要按各自规则实抓验证。

### 模式 D 收尾

- 跨章节一致性：通读两份文档，确认被删字段没有被其它章节当关联键引用。
- 两份文档正文产出后，由 orchestrator 落盘并把 `phase` 置为 `"done"`（Judge 不写
  manifest，也没有工具去写）。

### 字段采集表编写检查清单

```
□ 系统生成字段：示例="—", 路径="—", 规则="系统生成", 来源="无需采集，前端传入"
□ 无法采集字段：示例="—", 路径="—", 规则="无法采集", 来源="/"
□ 采集字段：示例=实际值(中文优先), 路径=中文菜单路径/见截图, 规则="采集字段", 来源="接口/页面字段"
□ 字段编号按标准字段定义逐模块从 1 起、模块内不跳号（跨模块会重号，跨模块引用写「模块号-字段号」）
□ 一对一：一个字段只有一个来源，无一对多/多对一
□ 字段表格式：| 字段英文名 | 字段中文名 | 字段编号 | 字段类型 | 示例 | 采集页面路径 | 采集规则 | 字段来源 |
□ 截图标注：采集路径红框（面包屑/左菜单/Tab）+ 页面可见字段红框（表头列标题+字段编号），两者均必标
□ 接口独有字段：字段来源列写接口路径（API{n}: resp_data.<实体>.<字段>），用「接口字段说明方式」
□ 每张表含截图标注引用 + files/ 存档 + 内嵌 curl
□ 系统无对应模块：不写字段采集表，仅强调板块不存在
□ 鉴权方式 + 数据返回方式在系统信息表必须体现
```
